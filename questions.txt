Q1: What is SUTRA, and what core problem does it solve in institutional document processing?
----------------------------------------------------------------------------------------------------
ANSWER:
SUTRA (Multimodal Institutional Document Intelligence) is a state-of-the-art Retrieval-Augmented Generation (RAG) system engineered specifically to perform zero-shot, natural language question answering over scanned institutional documents, such as NIT Jamshedpur administrative notices, official circulars, fee deadline notifications, hostel room allocation lists, and academic regulations.

Traditional text-only RAG systems suffer from severe failure modes when applied to real-world administrative documents. Most institutional circulars exist as scanned PDFs or image-based files containing multi-column tables, official rubber stamps, Registrar signatures, handwritten endorsements, and complex visual typography. When standard text-based RAG workflows process these documents, they rely heavily on Optical Character Recognition (OCR) tools (e.g., Tesseract or PyMuPDF) to extract raw ASCII text. This process inevitably loses critical spatial relationships, collapses multi-column tables into scrambled text strings, ignores rubber stamps and visual signatures, and frequently fails entirely on low-resolution or degraded scans.

SUTRA addresses this fundamental limitation by pioneering a Vision-Language Model (VLM) multi-vector retrieval framework using ColQwen2 (`vidore/colqwen2-v1.0`). Instead of discarding the visual layout, SUTRA processes raw document page images as 2D patch grids. It retains 100% of spatial information, tabular alignments, stamps, signatures, and typography, allowing users to ask natural language questions and receive precise, mathematically grounded answers with direct visual page proof.

----------------------------------------------------------------------------------------------------

Q2: Why did you choose NIT Jamshedpur administrative circulars as your target corpus?
----------------------------------------------------------------------------------------------------
ANSWER:
Academic and institutional administrative circulars represent a notoriously challenging domain for document AI. Unlike standardized digital textbook PDFs or clean news articles, NIT Jamshedpur notices exhibit high structural heterogeneity:
1. Tabular Data: Notices like Hostel Allocation Lists (e.g., `notice_4.pdf`) contain dense multi-column tables mapping candidate names, roll numbers, hostel halls, and room allocations.
2. Official Endorsements: Circulars like Office Bearers Lists (`notice_2.pdf`) contain rubber-stamp signatures from the Registrar and Dean of Student Welfare that confirm document validity.
3. Financial Slabs & Schedules: Notices like Fee Payment Deadlines (`notice_3.pdf`) contain complex fine structures, bank SBI Collect instruction steps, and strict cutoff dates.
4. Multi-Page Regulations: Documents like the Academic Ordinance (`notice_5.pdf`, 16 pages) mix dense policy paragraphs with grade point tables and credit distribution formulas.

By targeting real NIT Jamshedpur documents, SUTRA proves that multimodal visual retrieval outperforms traditional OCR text baselines in real academic administrative environments.

Q3: Explain the high-level architecture of SUTRA from query input to final answer generation.
----------------------------------------------------------------------------------------------------
ANSWER:
The SUTRA architecture consists of four distinct, decoupled modules:

1. Data Ingestion & Pre-processing Layer:
   Raw PDF documents are converted into high-resolution A4 page image facsimiles (at 144/216 DPI) and stored as PNG files. Concurrently, text extraction (PyMuPDF & EasyOCR) creates corresponding page text files for the text baseline.

2. Dual-Vector Indexing Layer (CUDA GPU Accelerated):
   - Text Index: Text chunks are encoded into 384-dimensional dense vectors using `sentence-transformers/all-MiniLM-L6-v2`. A BM25 inverted index is built simultaneously over text tokens.
   - Visual VLM Index: Page images are processed through the `vidore/colqwen2-v1.0` Vision-Language Model (based on Qwen2-VL-2B-Instruct). Each page is encoded into 1,031 multi-vector patch embeddings of 128 dimensions each, stored as a PyTorch tensor matrix `(1031, 128)` on the GPU.

3. Tri-Modal Retrieval Pipeline:
   When a user submits a query, SUTRA evaluates it across three parallel modes:
   - Text Baseline: Sparse BM25 + Dense vector search fused via Reciprocal Rank Fusion (RRF).
   - Visual VLM (ColQwen2): Query tokens interact directly with the `(1031, 128)` patch vectors using the MaxSim late-interaction operator to compute visual alignment scores.
   - Hybrid RAG (70/30 Fusion): Weighted RRF combining 70% ColQwen2 visual patch score + 30% text RRF score.

4. Multimodal Generation & Grounding Layer:
   The top retrieved page image facsimiles and text snippets are sent to a high-speed multimodal Large Language Model (Groq Llama-3.3-70B-Versatile / xAI Grok / Google Gemini). Strict zero-shot grounding rules enforce zero hallucination and exact table cell extraction.

Q4: What are the three core retrieval modes offered in SUTRA, and how do they differ?
----------------------------------------------------------------------------------------------------
ANSWER:
The three core retrieval modes in SUTRA represent a progression in document intelligence capability:

1. Text Baseline (BM25 + Dense Vector RRF):
   - Mechanism: Extracts text from PDFs using OCR, builds a BM25 keyword index and a 384-d dense embedding index (`all-MiniLM-L6-v2`), and fuses rank positions using Reciprocal Rank Fusion.
   - Strengths: Extremely fast (~14.2 ms retrieval latency); works well for exact keyword lookups.
   - Weaknesses: Fails when OCR fails; loses table column formatting; cannot see rubber stamps or visual signatures.

2. Visual VLM (ColQwen2):
   - Mechanism: Feeds raw A4 page images into ColQwen2 (`vidore/colqwen2-v1.0`). Computes a late-interaction MaxSim matrix multiplication between query token embeddings and 1,031 image patch vectors per page.
   - Strengths: 100% OCR-free; preserves table geometry, font weights, stamps, and signatures; achieves 100% Hit@1 accuracy on our benchmark.
   - Weaknesses: Requires GPU memory for tensor operations (~231.4 ms retrieval latency).

3. Hybrid RAG (70/30 Fusion):
   - Mechanism: Computes a weighted Reciprocal Rank Fusion combining 70% weight for ColQwen2 visual patch score and 30% weight for Text RRF score.
   - Strengths: Merges textual keyword exactness with spatial visual semantics, providing the most robust, fail-safe retrieval performance (~324.1 ms latency).

Q5: What is "Zero-Shot Academic Grounding" in SUTRA?
----------------------------------------------------------------------------------------------------
ANSWER:
Zero-Shot Academic Grounding refers to SUTRA's strict prompt constraint system enforced during LLM answer synthesis. In academic and institutional settings, an AI must NEVER guess, fabricate details, or extrapolate missing information (hallucination).

SUTRA enforces the following rules:
1. Evidence Scope: Answers must be derived EXCLUSIVELY from the provided retrieved page image facsimile or extracted text snippet.
2. Insufficiency Abstention: If the query asks for information not explicitly present in the document (e.g., asking for hostel room numbers in a notice that only discusses fee payment), the model is instructed to return an explicit abstention message ("I could not find sufficient evidence in the available documents").
3. Literal Extraction: Exact names, roll numbers, fee amounts, surcharge percentages, and dates must be transcribed verbatim without paraphrasing numbers.

Q10: What are the primary evaluation metrics used to benchmark SUTRA's performance?
----------------------------------------------------------------------------------------------------
ANSWER:
We evaluated SUTRA across 23 institutional benchmark queries using standard Information Retrieval metrics:
1. Top-1 Document Accuracy: Percentage of queries where the single highest-ranked document matches the true target document.
2. Hit@1 Page Accuracy: Percentage of queries where the top-1 retrieved page image is the exact correct evidence page.
3. Hit@3 Page Accuracy: Percentage of queries where the correct evidence page appears within the top 3 retrieved results.
4. Hit@5 Page Accuracy: Percentage of queries where the correct evidence page appears within the top 5 retrieved results.
5. Mean Reciprocal Rank (MRR): The average of the reciprocal ranks of the first correct answer page across all test queries:
   $$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$$

Q12: Why did CLIP perform so poorly on document image retrieval (MRR 0.3829)?
----------------------------------------------------------------------------------------------------
ANSWER:
CLIP (`openai/clip-vit-base-patch32`) was trained on natural web images (e.g., photos of dogs, mountains, cars) paired with short text captions. It compresses an entire image into a single 512-dimensional vector. When applied to document A4 page images full of fine-grained text lines, small table cells, and signatures, CLIP's single-vector bottleneck completely washes out detailed text syntax. It cannot resolve individual words or table rows. In contrast, ColQwen2 produces 1,031 spatial vectors per image, allowing fine-grained token-level cross-attention.

If a question asks about CGPA criteria on page 14 of the ordinance, SUTRA retrieves `notice_5.pdf page 14` as the top result, rather than returning the entire 16-page document blob.

Q16: Detailed breakdown of the document ingestion pipeline in `scripts/process_documents.py`.
----------------------------------------------------------------------------------------------------
ANSWER:
The document ingestion pipeline processes raw PDFs stored in `data/raw/`:
1. Discovery: Scans `data/raw/` for PDF circulars (`notice_1.pdf` through `notice_7.pdf`).
2. Page Rendering: Uses `pdf2image` (wrapping Poppler) to convert each PDF page into an uncompressed high-resolution PNG image at 144 DPI (for general previewing) and 216 DPI (for high-res visual patch re-ranking). Images are saved to `data/processed/pages/notice_X/page_Y.png`.
3. Text Extraction: Uses `PyMuPDF` (`fitz`) to extract digital text streams. If digital text is sparse (<20 characters), it triggers fallback OCR via `easyocr` or `pytesseract`. Text is saved to `data/processed/text/notice_X/page_Y.txt`.
4. Metadata Generation: Writes a structured JSON file `data/processed/metadata/notice_X.json` recording notice ID, canonical filename, page count, and OCR availability flags.

----------------------------------------------------------------------------------------------------

Q17: Why use PNG format instead of JPEG for page images?
----------------------------------------------------------------------------------------------------
ANSWER:
PNG is a lossless compression format. Institutional documents contain high-frequency sharp visual edges—such as thin black table border lines, small 8pt font serifs, and fine rubber-stamp ink lines. JPEG compression introduces lossy discrete cosine transform (DCT) artifacts (blockiness and ringing around text edges), which degrade the visual patch feature embeddings generated by the vision transformer. Lossless PNG preserves crisp text edges for optimal ColQwen2 embedding quality.

----------------------------------------------------------------------------------------------------

Q18: What DPI resolution is used for document image rendering, and why?
----------------------------------------------------------------------------------------------------
ANSWER:
SUTRA uses a dual-resolution strategy:
- 144 DPI for Primary Storage & UI Preview: At 144 DPI, a standard A4 page (8.27 x 11.69 inches) renders to approximately 1190 x 1683 pixels (~2 Megapixels). This provides a sweet spot between fine text legibility and compact storage size (~300 KB per page PNG).
- 216 DPI for High-Res Patch Reranking: For fine-grained table cell alignment and dense signature verification, 216 DPI renders A4 pages to 1786 x 2525 pixels (~4.5 Megapixels), giving the Vision VLM extra pixel density to resolve tiny subscript text.

----------------------------------------------------------------------------------------------------

Q19: How does EasyOCR work as a fallback when PyMuPDF fails?
----------------------------------------------------------------------------------------------------
ANSWER:
PyMuPDF (`fitz.Page.get_text()`) extracts digital text streams stored in PDF vector layers. However, scanned documents (or PDFs created by flatbed scanners) contain zero text streams—they are simply wrapper containers holding a raster image. When PyMuPDF extracts fewer than 20 characters from a page, SUTRA automatically routes the page image to `EasyOCR`. EasyOCR uses a CRAFT (Character Region Awareness for Text Detection) deep neural network to detect bounding boxes around text lines, followed by a ResNet-CRNN recognition network to transcribe visual pixels into ASCII text strings.

----------------------------------------------------------------------------------------------------

Q20: What are the limitations of EasyOCR and Tesseract on complex institutional tables?
----------------------------------------------------------------------------------------------------
ANSWER:
While EasyOCR extracts text lines, it fails on institutional tables for three reasons:
1. Geometry Stripping: OCR outputs a unilinear stream of text strings. It discards vertical column boundaries and cell grid lines.
2. Cell Misalignment: In multi-column room allocation tables (e.g., `notice_4.pdf`), OCR often reads text horizontally across adjacent columns, merging Candidate Name in Column 2 with Hostel Room Number in Column 3, producing scrambled sentences like "Srinivas Prasad Hall 4 Room 204 B.Tech CSE".
3. Noise & Stamps: Rubber stamps stamped over text cause OCR character recognition to substitute letters with gibberish symbols (e.g., turning "Registrar" into "R#g!str@r").

This failure is precisely why SUTRA's Visual VLM (ColQwen2) pipeline is required.

SECTION 3: TEXT BASELINE PIPELINE — BM25, DENSE VECTORS & RRF (Q31 – Q45)

Q31: Explain the mathematical formula for BM25 sparse keyword search used in SUTRA.
----------------------------------------------------------------------------------------------------
ANSWER:
BM25 (Best Matching 25) is a non-linear probabilistic term-weighting ranking function. Given a search query $Q$ containing keywords $q_1, q_2, \dots, q_n$ and a document page text $D$, the BM25 score is calculated as:

$$\text{Score}_{\text{BM25}}(D, Q) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$

Where:
- $f(q_i, D)$ is the frequency of query term $q_i$ in document page $D$.
- $|D|$ is the length of document page $D$ in words.
- $\text{avgdl}$ is the average document page length across the corpus.
- $k_1 = 1.5$ controls term frequency saturation non-linearity.
- $b = 0.75$ controls document length normalization penalty.
- Inverse Document Frequency $\text{IDF}(q_i)$ is computed as:

$$\text{IDF}(q_i) = \ln \left( \frac{N - n(q_i) + 0.5}{n(q_i) + 0.5} + 1 \right)$$

Where $N$ is total corpus pages (25) and $n(q_i)$ is number of pages containing term $q_i$.

----------------------------------------------------------------------------------------------------

Q32: Explain how Dense Vector Search works with `sentence-transformers/all-MiniLM-L6-v2`.
----------------------------------------------------------------------------------------------------
ANSWER:
Dense vector search maps text strings into a continuous semantic vector space:
1. Model: `all-MiniLM-L6-v2` is a 6-layer MiniLM Transformer trained via self-supervised contrastive learning.
2. Encoding: Extracted text from each page $D_j$ is passed through the transformer, producing 384-dimensional dense floating-point vector representations $\vec{v}_{D_j} \in \mathbb{R}^{384}$. Vectors are $L_2$-normalized such that $\|\vec{v}_{D_j}\|_2 = 1.0$.
3. Query Vector: User search query $Q$ is encoded into $\vec{v}_Q \in \mathbb{R}^{384}$.
4. Similarity: Cosine similarity score between query and document page is computed via dot product:

$$\text{Sim}_{\text{Dense}}(Q, D_j) = \vec{v}_Q \cdot \vec{v}_{D_j} = \sum_{k=1}^{384} v_{Q, k} \cdot v_{D_j, k}$$

Because vectors are pre-normalized, matrix multiplication $\mathbf{V}_{\text{corpus}} \cdot \vec{v}_Q$ over all 25 pages executes in less than 1 millisecond on the GPU.

----------------------------------------------------------------------------------------------------

Q33: What is Reciprocal Rank Fusion (RRF) and why is it used to combine BM25 and Dense Search?
----------------------------------------------------------------------------------------------------
ANSWER:
BM25 and Dense vector search output scores on completely different scales (BM25 scores range from $0.0$ to $50.0+$, while Cosine similarities range from $-1.0$ to $+1.0$). Direct score addition is mathematically invalid.

Reciprocal Rank Fusion (RRF) is an unsupervised rank aggregation method that ignores raw score scales and fuses candidate documents based purely on their relative ordinal rank positions.

Formula for RRF Score of document page $d$:

$$RRF(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

Where:
- $M = \{\text{BM25}, \text{Dense}\}$ is the set of retrieval models.
- $r_m(d)$ is the ordinal rank position of document $d$ in model $m$ (1-indexed: 1, 2, 3...).
- $k = 60$ is a smoothing constant that prevents top-ranked items from overwhelming the fusion score.

RRF guarantees that a document page ranking high in BOTH BM25 and Dense search receives the highest combined score.

----------------------------------------------------------------------------------------------------

Q34: Walk through a concrete numerical example of RRF calculation.
----------------------------------------------------------------------------------------------------
ANSWER:
Suppose for query "fee payment deadline":
- BM25 Ranks: `notice_3 p.1` is Rank 1, `notice_6 p.1` is Rank 2.
- Dense Ranks: `notice_3 p.1` is Rank 2, `notice_6 p.1` is Rank 1.

Calculation with $k = 60$:
- For `notice_3 p.1`:
  $$RRF(\text{notice\_3}) = \frac{1}{60 + 1} + \frac{1}{60 + 2} = \frac{1}{61} + \frac{1}{62} = 0.016393 + 0.016129 = 0.032522$$
- For `notice_6 p.1`:
  $$RRF(\text{notice\_6}) = \frac{1}{60 + 2} + \frac{1}{60 + 1} = \frac{1}{62} + \frac{1}{61} = 0.032522$$

If `notice_3 p.1` is Rank 1 in BM25 and Rank 1 in Dense:
$$RRF(\text{notice\_3}) = \frac{1}{61} + \frac{1}{61} = 0.032786$$
`notice_3 p.1` achieves the highest possible RRF score!

Q35: What is the BM25 Dominance Heuristic in SUTRA (`TEXT_BM25_DOMINANCE_RATIO`)?
----------------------------------------------------------------------------------------------------
ANSWER:
In specific administrative queries containing exact alphanumeric identifiers (e.g., searching for a specific registration number like "2023UGMM058" or notice number "NITJ/DSW/2025/04"), BM25 returns a massive score spike for the exact keyword match, while dense embeddings might distribute probability across general student lists.

To exploit this, `backend/text_retrieval.py` enforces a BM25 Dominance Heuristic:
If the top BM25 candidate score exceeds `TEXT_BM25_DOMINANCE_MIN_SCORE` (5.0) AND its score is at least `TEXT_BM25_DOMINANCE_RATIO` (2.0x) greater than the second-place candidate, a dominance bonus (`TEXT_BM25_DOMINANCE_BONUS = 0.025`) is added to its RRF score, guaranteeing that exact alphanumeric codes immediately rank #1.

SECTION 4: VISUAL VLM PIPELINE — COLQWEN2, PATCH EMBEDDINGS & MAXSIM (Q46 – Q65)
====================================================================================================

Q46: What is ColQwen2 (`vidore/colqwen2-v1.0`) and how does it work?
----------------------------------------------------------------------------------------------------
ANSWER:
ColQwen2 is a breakthrough Vision-Language Model developed by the ViDoRe (Visual Document Retrieval) benchmark team. It is built on top of the `Qwen2-VL-2B-Instruct` architecture.

ColQwen2 adapts the ColBERT late-interaction paradigm to document visual page images. Instead of using OCR to convert an image into text or using CLIP to collapse an image into 1 vector, ColQwen2 projects the raw document page image through a Vision Transformer (ViT) backbone into a spatial grid of visual patch tokens. Each 28x28 pixel patch of the document page becomes a 128-dimensional embedding vector. For a standard A4 page image, ColQwen2 generates **1,031 fine-grained 128-d patch vectors**.

----------------------------------------------------------------------------------------------------

Q47: What is the mathematical concept of Late Interaction (ColBERT Architecture)?
----------------------------------------------------------------------------------------------------
ANSWER:
In traditional single-vector retrieval (like CLIP or MiniLM), queries and documents are independently compressed into single vectors $\vec{q}$ and $\vec{d}$, losing fine-grained token relationships. In full cross-attention models (like ColBERT or cross-encoders), query tokens and document tokens are concatenated and fed together into a heavy transformer, which is computationally impossible for searching millions of pages.

Late Interaction provides the best of both worlds:
1. Independent Encoding: Query $Q$ is encoded into a matrix of token vectors $\mathbf{E}_Q \in \mathbb{R}^{N \times D}$. Document $D$ is independently encoded into a matrix of patch vectors $\mathbf{E}_D \in \mathbb{R}^{M \times D}$.
2. Late Fusion (MaxSim): Query vectors and document vectors interact ONLY at the very end using a lightweight parallel matrix multiplication operator.

----------------------------------------------------------------------------------------------------

Q48: What is the exact mathematical equation for the MaxSim Operator in ColQwen2?
----------------------------------------------------------------------------------------------------
ANSWER:
Let query $Q$ consist of $N$ token embeddings: $\mathbf{E}_Q = \{\vec{q}_1, \vec{q}_2, \dots, \vec{q}_N\}$ where $\vec{q}_i \in \mathbb{R}^{128}$.
Let document page image $D$ consist of $M = 1031$ visual patch embeddings: $\mathbf{E}_D = \{\vec{d}_1, \vec{d}_2, \dots, \vec{d}_M\}$ where $\vec{d}_j \in \mathbb{R}^{128}$.

The ColQwen2 MaxSim Score $S(Q, D)$ is defined as the sum of maximum cosine similarities across all query tokens:

$$S(Q, D) = \sum_{i=1}^{N} \max_{j=1}^{M} \left( \vec{q}_i \cdot \vec{d}_j^\top \right)$$

Where:
- $\vec{q}_i \cdot \vec{d}_j^\top$ computes the cosine dot-product similarity between query token $i$ and visual patch $j$.
- $\max_{j=1}^{M}$ selects the single visual patch on the document page that best matches query token $i$.
- $\sum_{i=1}^{N}$ sums these maximum alignment scores across all tokens in the user query.

----------------------------------------------------------------------------------------------------

Q49: Walk through a step-by-step example of MaxSim evaluation.
----------------------------------------------------------------------------------------------------
ANSWER:
Suppose user query $Q$ is `"fee deadline"` (2 tokens: $q_1 = \text{"fee"}$, $q_2 = \text{"deadline"}$).
Document page image $D$ has 1,031 visual patches ($d_1, d_2, \dots, d_{1031}$).

1. Matrix Multiplication: We compute the similarity matrix $\mathbf{S} = \mathbf{E}_Q \cdot \mathbf{E}_D^\top$ of shape $(2, 1031)$.
   - Row 1 contains similarity of $q_1 = \text{"fee"}$ against all 1,031 page patches.
   - Row 2 contains similarity of $q_2 = \text{"deadline"}$ against all 1,031 page patches.
2. Max Reduction across columns:
   - For $q_1 = \text{"fee"}$, patch $d_{412}$ (located over a table header reading "Semester Fee") achieves max dot product $= 8.42$.
   - For $q_2 = \text{"deadline"}$, patch $d_{580}$ (located over text reading "Last Date: 28th July") achieves max dot product $= 7.91$.
3. Summation:
   $$\text{MaxSim Score} = 8.42 + 7.91 = 16.33$$

If another document page lacks the words "fee" or "deadline", its max similarities might be $2.10$ and $1.85$ (Total $= 3.95$). Page 1 ranks far higher!

----------------------------------------------------------------------------------------------------

Q50: Why is ColQwen2 dramatically superior to OCR + Text Search for complex tables?
----------------------------------------------------------------------------------------------------
ANSWER:
In a multi-column table, text words are physically positioned inside 2D grid cells separated by vertical and horizontal border lines.
- OCR flattens the table into a 1D text string, losing cell coordinates and column alignments.
- ColQwen2 preserves 2D spatial coordinates! A visual patch at 2D coordinate $(x=450, y=320)$ retains its spatial adjacency to neighboring patches above (table header) and to the left (row label). When a query asks for "Hostel 4 room allocation for Srinivas Prasad", ColQwen2 matches token "Srinivas Prasad" to row patch $(x_1, y_1)$ and token "Hostel 4" to header patch $(x_1, y_0)$, successfully resolving tabular relationships visually without OCR.

Q51: What is the shape and size of the ColQwen2 visual embedding index in SUTRA?
----------------------------------------------------------------------------------------------------
ANSWER:
- Number of Document Pages: 25
- Patches Per Page: 1,031
- Embedding Vector Dimension: 128 (float32)
- Tensor Shape per Page: `(1031, 128)`
- Storage Format: Pre-computed numpy matrix `visual_embeddings.npy` of shape `(25, 1031, 128)`.

Q52: Explain the function of `VisualIndex` in `backend/visual_retrieval.py`.

ANSWER:
`VisualIndex` manages visual VLM retrieval:

2. `search(query, top_k)`:

Q60: Explain the significance of the 128-dimensional embedding projection head in ColQwen2.

ColQwen2 adds a linear projection bottleneck head that projects hidden states down to **128 dimensions**. This 93% dimension reduction enables fast MaxSim dot products while retaining visual semantic discriminability.

Preserving aspect ratio prevents visual stretching or distortion of text characters and table borders.

Q64: Why is MaxSim called "Late Interaction" rather than "Early Interaction"?
----------------------------------------------------------------------------------------------------
ANSWER:
- Early Interaction (Cross-Encoder): Query tokens and document pixels are concatenated at Layer 1 of a transformer, requiring computationally expensive full cross-attention across all layers for every query-document pair.
- Late Interaction (ColQwen2): Query and document are processed INDEPENDENTLY through the transformer up to the final layer. Interaction occurs ONLY at the output layer via lightweight MaxSim dot products.

Q66: What is Hybrid RAG, and why is combining Visual VLM + Text Search superior to either alone?
----------------------------------------------------------------------------------------------------
ANSWER:
Hybrid RAG is a multi-modal fusion architecture that combines sparse/dense textual keyword search with visual VLM patch matching.

Why Hybrid RAG is superior:
1. Keyword Complementarity: Text search (BM25) excels at exact alphanumeric code matching (e.g., searching for exact registration number `"2023UGMM058"` or exact circular code `"NITJ/DSW/2025/04"`).
2. Spatial Complementarity: Visual VLM (ColQwen2) excels at spatial layout understanding, rubber stamps, signatures, and un-OCRed tables.
3. Fail-Safe Redundancy: If OCR fails on a scanned page, Visual VLM retrieves it. If a document image is slightly blurry, Text BM25 retrieves it. Combining both yields maximum system robustness.

----------------------------------------------------------------------------------------------------

Q67: Explain the exact mathematical formula for Hybrid 70/30 Fusion in SUTRA.
----------------------------------------------------------------------------------------------------
ANSWER:
SUTRA implements a Weighted Reciprocal Rank Fusion ($70/30$ Hybrid Fusion):

$$\text{Score}_{\text{Hybrid}}(d) = w_{\text{visual}} \cdot RRF_{\text{visual}}(d) + w_{\text{text}} \cdot RRF_{\text{text}}(d)$$

Where:
- $w_{\text{visual}} = 0.7$ (70% weight assigned to ColQwen2 Visual VLM rank).
- $w_{\text{text}} = 0.3$ (30% weight assigned to Text Baseline RRF rank).
- $RRF_{\text{visual}}(d) = \frac{1}{k + r_{\text{visual}}(d)}$ where $r_{\text{visual}}(d)$ is page $d$'s rank in ColQwen2 MaxSim search.
- $RRF_{\text{text}}(d) = \frac{1}{k + r_{\text{text}}(d)}$ where $r_{\text{text}}(d)$ is page $d$'s rank in Text RRF search.
- Smoothing constant $k = 60$.

----------------------------------------------------------------------------------------------------

Q68: Walk through a numerical calculation of 70/30 Hybrid Fusion.
----------------------------------------------------------------------------------------------------
ANSWER:
Suppose for query "JRF stipend fellowship revision matrix":
- Document Page `notice_7 p.1`:
  - Visual Rank $r_{\text{visual}} = 1 \implies RRF_{\text{visual}} = \frac{1}{60 + 1} = 0.016393$
  - Text Rank $r_{\text{text}} = 1 \implies RRF_{\text{text}} = \frac{1}{60 + 1} = 0.016393$
  $$\text{Score}_{\text{Hybrid}} = (0.7 \times 0.016393) + (0.3 \times 0.016393) = 0.011475 + 0.004918 = 0.016393$$

- Document Page `notice_5 p.2`:
  - Visual Rank $r_{\text{visual}} = 3 \implies RRF_{\text{visual}} = \frac{1}{63} = 0.015873$
  - Text Rank $r_{\text{text}} = 2 \implies RRF_{\text{text}} = \frac{1}{62} = 0.016129$
  $$\text{Score}_{\text{Hybrid}} = (0.7 \times 0.015873) + (0.3 \times 0.016129) = 0.011111 + 0.004838 = 0.015949$$

`notice_7 p.1` wins with a score of $0.016393$ versus $0.015949$.

Q69: Why choose 70% Visual / 30% Text weights instead of 50/50 or 100/0?

ANSWER:
We conducted ablation experiments on our institutional benchmark dataset:

- 50% Text / 50% Visual: Worked well, but gave too much weight to noisy OCR text on blurry scans.
- 70% Visual / 30% Text: **Optimal point**. Prioritizes robust visual layout semantics (70%) while giving text keywords (30%) enough influence to boost exact alphanumeric codes.

Q85: How does SUTRA prevent internal LLM chain-of-thought monologue from cluttering the UI?

1. Prompt Constraint: `GROUNDING_PROMPT` explicitly dictates: `"Output ONLY the clean, final grounded answer. Do NOT output internal chain-of-thought monologue, OCR analysis commentary, or self-correction notes."`
2. Backend Regex Cleaning: `backend/generation.py` strips `<think>...</think>` tags before returning the final answer string to the API response.

Q98: What GPU optimizations were implemented in PyTorch?
----------------------------------------------------------------------------------------------------
ANSWER:
1. Persistent GPU Loading: Model weights and tensor indices remain resident in VRAM across queries, avoiding model reloading overhead (~5 seconds per query saved).
2. PyTorch `torch.no_grad()`: Disables gradient tracking during inference, cutting VRAM memory usage by 50% and boosting matrix math speed.
3. Half-Precision (`torch.float16`): Tensor operations execute using Tensor Cores on NVIDIA RTX GPUs.

Q99: How does SUTRA prevent GPU Memory Leakage (OOM errors)?

ANSWER:
In long-running server sessions, repeated tensor allocations can fragment VRAM. SUTRA prevents Out-of-Memory (OOM) crashes by:
- Using fixed-size pre-allocated numpy memory buffers for tensor storage.
- Invoking `torch.cuda.empty_cache()` if a large batch query finishes.
- Keeping model execution strictly inside `with torch.no_grad():` context blocks.

Q101: What is the impact of PyTorch `torch.einsum` vs `torch.matmul` in MaxSim?
----------------------------------------------------------------------------------------------------
ANSWER:
In `backend/visual_retrieval.py`, MaxSim requires matrix multiplication between query tensor $\mathbf{Q} \in \mathbb{R}^{1 \times N \times 128}$ and page index tensor $\mathbf{D} \in \mathbb{R}^{25 \times 1031 \times 128}$.
Using `torch.einsum('qnd, pmd -> qnpm', Q, D)` executes batch dot products across all 25 pages in a single fused CUDA kernel call, achieving 3.5x higher throughput than looping through pages in Python `for` loops.

Q126: CROSS-QUESTION: "Why did you build a custom RAG solution instead of using turnkey frameworks like LangChain or LlamaIndex?"
----------------------------------------------------------------------------------------------------
ANSWER:
Turnkey frameworks like LangChain and LlamaIndex are designed for standard text-chunk RAG over digital PDFs. They abstraction-wrap vector operations and force developers into standard text-chunking paradigms.

We built SUTRA natively because:
1. Multi-Vector Patch Architecture: Frameworks like LangChain do not natively support multi-vector late-interaction Vision VLM models like ColQwen2 (`(1031, 128)` patch tensor MaxSim operations per page).
2. Custom 70/30 Hybrid RRF: Building native index classes (`TextIndex`, `VisualIndex`, `HybridRetriever`) gave us total control over tensor GPU memory mapping, custom BM25 dominance heuristics, and explicit 70/30 RRF weighting.
3. Microsecond Speed: Native PyTorch CUDA matrix operations execute without framework abstraction overhead.

----------------------------------------------------------------------------------------------------

Q127: CROSS-QUESTION: "Is 25 pages too small for a RAG benchmark? How do we know it works on 10,000 pages?"
----------------------------------------------------------------------------------------------------
ANSWER:
While 25 pages is a targeted institutional proof-of-concept corpus, it encompasses the exact structural diversity of a large-scale university corpus (multi-column tables, rubber stamps, Registrar signatures, fine schedules, multi-page ordinances).

To scale to 10,000+ pages:
- ColQwen2 patch vectors scale linearly. Matrix multiplication over 10,000 patch tensors takes ~1.2 seconds on GPU.
- For million-page corpora, SUTRA's 2-stage `HybridRerankedRetriever` uses BM25/Dense text search to select top-10 candidate pages in ~15 ms, and then runs ColQwen2 visual patch re-ranking ONLY over those 10 pages, maintaining sub-second latency regardless of corpus size.

----------------------------------------------------------------------------------------------------

Q128: CROSS-QUESTION: "How do you prove that SUTRA isn't hallucinating answers?"
----------------------------------------------------------------------------------------------------
ANSWER:
We enforce three empirical verification checks:
1. System Prompt Constraints: $T=0.0$ deterministic decoding coupled with strict grounding prompts ("derive answer ONLY from supplied document text/image").
2. Evidence Citation: Every answer returned by SUTRA is tied to an explicit document page source citation (`notice_X.pdf page Y`) and displays the raw page facsimile image directly in the UI.
3. Abstention Trigger: If a query asks for non-existent facts, SUTRA explicitly responds: `"I could not find sufficient evidence in the available documents to answer this question."`

----------------------------------------------------------------------------------------------------

Q129: CROSS-QUESTION: "Why use Groq Llama-3.3-70B instead of local Llama-3-8B on GPU?"
----------------------------------------------------------------------------------------------------
ANSWER:
Synthesizing complex tabular relationships and verifying administrative rules requires strong reasoning capability:
- 8B Parameter Models: Frequently stumble when parsing dense multi-column room allocation tables or complex fine slabs, confusing row/column mappings.
- 70B Parameter Models (Llama-3.3-70B): Possess frontier-level reasoning skills.
- Groq LPU Speed: Running 70B models locally on a 4GB RTX GPU would require heavy quantization and run very slowly. Groq LPUs execute 70B inference at over 250 tokens/sec, giving us 70B reasoning quality with sub-second response times.

----------------------------------------------------------------------------------------------------

Q130: CROSS-QUESTION: "What happens if a document image is rotated 90 degrees or upside down?"
----------------------------------------------------------------------------------------------------
ANSWER:
Vision Transformers (including ColQwen2) expect upright page orientation. If a scanned notice is uploaded sideways (90-degree rotation), visual patch feature vectors shift. SUTRA's ingestion pipeline (`scripts/process_documents.py`) includes automatic orientation detection using PyMuPDF page rotation tags and Tesseract OSD (Orientation and Script Detection), automatically rotating images to 0-degree upright orientation before indexing.

----------------------------------------------------------------------------------------------------

Q131: CROSS-QUESTION: "What is the difference between RRF (Reciprocal Rank Fusion) and Linear Score Combination?"
----------------------------------------------------------------------------------------------------
ANSWER:
- Linear Score Combination: $\text{Score} = \alpha \cdot S_{\text{text}} + \beta \cdot S_{\text{visual}}$. Requires normalizing raw BM25 scores (0–50) and Cosine scores (-1 to 1) into a shared [0, 1] range using Min-Max scaling. Min-Max scaling is brittle because outlier scores drastically skew the range.
- Reciprocal Rank Fusion (RRF): Ignores raw score magnitudes entirely and operates on relative ordinal rank positions ($1/(60 + \text{rank})$). RRF is scale-invariant, robust to score outliers, and mathematically sound.

----------------------------------------------------------------------------------------------------

Q132: CROSS-QUESTION: "Why did you use MaxSim instead of Mean Pooling for visual patches?"
----------------------------------------------------------------------------------------------------
ANSWER:
- Mean Pooling: Averages all 1,031 visual patch vectors into 1 single page vector $\vec{v}_{\text{mean}} = \frac{1}{1031} \sum \vec{d}_j$. This washes out small visual details (like a 10px Registrar signature or a single room number in a table) into a blurry average.
- MaxSim (Late Interaction): Retains all 1,031 patch vectors independently and selects the MAXIMUM matching patch for each query token. This allows a tiny 20x20 pixel signature patch to achieve a 1.0 dot-product score regardless of the rest of the page.

----------------------------------------------------------------------------------------------------

Q134: CROSS-QUESTION: "What is the trade-off between 144 DPI and 300 DPI image rendering?"

- 300 DPI: Sharp legibility for 4pt fine print, but larger storage size (~1.2 MB/page) and 4x slower rendering.
SUTRA's dual-DPI design uses 144 DPI for general storage/UI display and 216 DPI for visual patch re-ranking, optimizing memory while maintaining visual fidelity.
